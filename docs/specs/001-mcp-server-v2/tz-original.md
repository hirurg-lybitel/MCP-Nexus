# MCP-сервер для учётной системы: концептуальное ТЗ

Oct 28, 2026 · @Andrei K

## Цель и контекст

Нужно разработать MCP-сервер **только для чтения**, через который пользователи бухгалтерской системы работают с данными на естественном языке в **Claude Desktop** или **Codex**. Сервер должен поддерживать не только справочные вопросы («какое сальдо по 62 на 1 октября»), но и многошаговый анализ. Пример: «проанализируй, почему упала прибыль за прошлый квартал, с учётом изменений во внешней экономической среде, и дай рекомендации по улучшению финансовой ситуации».

**Исходные условия:**

- Система работает на **Firebird**. Версия 5.0. Для MCP-сервера поднимается реплика БД, обновляемая раз в сутки. Реплика доступна для записи: отчётному воркеру gedemin.exe это нужно.
- Хозяйственная операция оформляется документом. Проводки по документу формируются программным кодом на VBScript.
- У каждого из сотен типов документов есть своя таблица с реквизитами. Метаданные системы полностью описывают эти таблицы, их поля и связи.
- В системе есть штатные отчёты со своим программным кодом. Пользователи считают их эталоном.
- Исходный код системы доступен: вызов отчётов и доступ к логике системы можно организовать так, как удобно.
- Ведётся полный подробный количественный учёт.
- Передача учётных данных облачным моделям разрешена. Источники внешних данных не ограничены.

**Пользователи:**

- **Бухгалтер / финансист.** Спрашивает о сальдо, оборотах, расчётах с контрагентами, ищет документы.
- **Руководитель / финансовый директор.** Ставит аналитические задачи: причины отклонений, динамика показателей, рекомендации.
- **Консультант / разработчик.** Разбирается, почему проводка или отчёт дали именно такой результат.

**Главный критерий качества:** числа в ответе модели совпадают с тем, что пользователь увидит в штатном отчёте за те же параметры. Правдоподобный, но неверный ответ хуже, чем отказ. В аналитических задачах каждый вывод опирается на проверяемые цифры или источники, а гипотезы явно отделены от фактов.

## Ключевые принципы

1. **Учётную логику считает сервер, а не модель.** Сальдо, обороты, иерархия счетов, внутренние проводки и итоги вычисляются той же логикой, что и в штатных отчётах. Модель выбирает инструмент и параметры, а затем интерпретирует результат.
2. **Гибридный доступ.** Основа — специализированные тулы и штатные отчёты. Нестандартные вопросы закрывает доступ на чтение к таблицам: учётное ядро — через небольшой набор представлений, таблицы документов — напрямую, по автоматически построенному описанию схемы.
3. **Параметры в бизнес-терминах.** Код счёта `"60.1"`, период `"2026-Q3"`, наименование контрагента. Внутренние ID модель получает только через тулы поиска.
4. **Компактные ответы с готовыми итогами.** По умолчанию возвращаются агрегаты, детализация — по запросу и со страницами. Модель не должна сама суммировать сотни чисел.
5. **Знания о предметной области — по требованию.** Карточки документов, каталог отчётов и описание представлений отдаются через тулы или MCP-ресурсы, а не целиком в системном промпте.
6. **Исходный код — источник знаний, а не контекст.** Код проводок и отчётов заранее перерабатывается в описания, представления и примеры. Сырой код выдаётся только в режиме разработчика.
7. **Только чтение.** Сервер ничего не изменяет в БД. Разграничение прав по пользователям на пилоте не реализуется. Запись данных в объём работ не входит.
8. **Рассуждает модель, факты даёт сервер.** Многошаговый анализ (план, гипотезы, проверка, выводы) выполняет модель на стороне клиента. Сервер обеспечивает воспроизводимые цифры и единые определения показателей: один и тот же вопрос даёт одни и те же числа.
9. **Внешние данные отделены от учётных.** Сведения об экономической среде модель получает из веб-поиска клиента или из отдельных тулов с официальными источниками и всегда указывает источник.

Модель находит сущности через поиск (уровень 2), считает учётными тулами и штатными отчётами (уровень 1) и пишет SQL только для нестандартных вопросов (уровень 3). База знаний готовится заранее из исходного кода и данных и помогает объяснять, откуда взялась цифра. Все вызовы проходят через единый слой ограничений (только чтение, лимиты) и аудита. Данные о внешней среде модель берёт из веб-поиска клиента или отдельных тулов с официальными рядами, а многошаговое рассуждение выполняет сама модель в Claude Desktop или Codex.

## Уровень 1: учётные тулы и штатные отчёты

Эти тулы дают числа, которые должны совпадать с системой. Реализация использует ту же логику или те же процедуры, что и штатные отчёты. Дублировать расчёт в коде сервера нельзя.

**Учётные тулы (первая очередь):**

| Тул | Назначение | Ключевые параметры |
| --- | --- | --- |
| `get_chart_of_accounts` | План счетов с иерархией, типом (А/П/АП), видами аналитики и подробным описанием счёта | ветка счета, глубина |
| `get_balance` | Сальдо на дату (свёрнутое и развёрнутое) | счёт, дата, аналитика, валюта |
| `get_trial_balance` | Оборотно-сальдовая ведомость | период, счета, разворот по аналитике |
| `get_account_card` | Карточка счёта: проводки с документами и текущим сальдо | счёт, период, аналитика, страница |
| `get_account_analysis` | Анализ счёта: обороты в разрезе корреспондирующих счетов | счёт, период |
| `get_journal_order` | Журнал-ордер по счёту | счёт, период |
| `get_documents` | Список документов с фильтрами | тип, период, контрагент, есть ли проводки |
| `get_document` | Документ целиком: шапка, позиции и сформированные проводки | ID или номер + дата |

**Соответствие штатным отчётам Гедемина.** Учётные тулы — обёртки над штатными бухгалтерскими отчётами платформы. Они построены на общем движке (иерархия классов `TgdvAcctBase` → `TgdvAcctLedger` → …), и сервис отчётов вызывает эти же классы без интерфейса.

| Тул | Штатный отчёт | Что добавляет к общим параметрам |
| --- | --- | --- |
| `get_trial_balance` | Оборотная ведомость (`TgdvAcctCirculationList`) | Расшифровка оборотов по дебету и кредиту |
| `get_journal_order` | Журнал-ордер | Группировка по аналитикам в заданном порядке с промежуточными итогами; расшифровка по дебету и кредиту; корреспонденция с субсчетами |
| `get_account_card` | Карта счета | Попроводочно, без группировки по аналитике; фильтр по корреспондирующему счёту с выбором Дт/Кт; объединение одинаковых проводок |
| `get_account_analysis` | Анализ счета | На вики не описан; параметры уточняются по исходному коду |

**Общие параметры** — единая схема для всех тулов, как в штатных отчётах:

- **Период:** начало и окончание.
- **Счета:** список кодов; «включать субсчета»; «включать внутренние проводки» (Дт и Кт на одном счёте).
- **Аналитика:** фильтр по значениям (контрагент, подразделение, документ и т. д.); группировка по списку аналитик в заданном порядке; уровень иерархии справочника. Кроме аналитик счёта доступны стандартные разрезы: счёт, валюта, дата, месяц, квартал, год. Разрезы по месяцам и кварталам пригодятся и аналитическим тулам для динамики.
- **Количественные показатели** — для счетов с количественным учётом.
- **Вывод сумм:** валюта, суммы в эквиваленте, масштаб, округление.
- **Компания холдинга** (по умолчанию — текущая).
- **Расширенное сальдо итого:** сальдо отдельно по дебету и кредиту или свёрнутое.

**Сохранённые конфигурации.** В системе есть сохранённые настройки отчётов, которые бухгалтеры уже сделали для себя. Они доступны через `list_report_configs()` и `run_report_config(имя, период)`. Модель может запустить знакомую пользователю настройку, например «Журнал-ордер по кассе», меняя только период.

**Переход от итога к деталям** повторяет путь в системе: журнал-ордер → карта счета → проводки → документ (`get_document`). Ответ каждого тула содержит параметры для следующего уровня, чтобы модель не собирала их заново.

Источник: [вики «Бухгалтерские отчеты»](https://gsbelarus.com/gs/wiki/index.php/Категория:Бухгалтерские_отчеты) (страницы 2009–2015 гг., часть — заглушки). Полный список параметров берётся из исходного кода классов отчётов.

**Штатные отчёты:**

- `list_reports(поиск)` возвращает название, назначение и описание параметров отчётов. Все отчёты в описания тулов не кладём.
- `run_report(id, параметры)` возвращает **данные**, а не печатную форму: строки и итоги в JSON.
- Отчёты, которые открывают диалоги или зависят от интерфейса, либо адаптируются к запуску без интерфейса, либо исключаются из каталога.
- Самые востребованные отчёты (по статистике использования) постепенно выносятся в отдельные тулы с понятными параметрами.

### Как вызываются отчёты: отчётный воркер

Отчёты считает сама платформа: на Windows-сервере работает отдельный экземпляр `gedemin.exe` (отчётный воркер), а MCP-сервер обращается к нему по HTTP. Так отчёты считаются тем же кодом, что и у пользователей. Разбор исходников показал, что большая часть нужного уже есть.

| Что нужно | Что уже есть в платформе | Что добавить |
| --- | --- | --- |
| Транспорт | Встроенный HTTP-сервер (`Component/gd_WebServerControl_unit.pas`, секция `[WEB SERVER]` в `gedemin.ini`). Скрипт регистрирует свои обработчики через `RegisterOnGetEvent`: запрос вызывает функцию из `gd_function` с GET/POST-параметрами и ответом по ссылке | Проверка общего секрета в обработчиках, отключение `/get_blob` (сейчас без авторизации и с SQL-инъекцией), ответ в UTF-8 |
| Старт воркера | Командная строка `/SN /USER /PASSWORD /RUN <RUID>` или автозадача: стартовый макрос регистрирует обработчики | — |
| Штатные бухгалтерские отчёты | Классы `TgdvAcct*` — невизуальные наборы данных с свойствами (`DateBegin`, `DateEnd`, `CompanyKey`, `WithSubAccounts`, `IncludeInternalMovement`…) и методами (`AddAccount`, `AddCorrAccount`, `AddCondition`, `AddGroupBy`, `BuildReport`, `Execute(ConfigID)` для сохранённых конфигураций из `AC_ACCT_CONFIG`). Зарегистрированы для VBScript (`obj_WrapperGSClasses.pas`) | Обработчик на VBScript: создать объект, задать параметры, открыть, отдать строки в JSON |
| Пользовательские отчёты | `rp_reportlist` + функции в `gd_function` (функция параметров, основная, событий). Основная функция возвращает набор данных `IgsQueryList`, до печатной формы. `BuildReportWithParam` и `System.ExecuteScriptFunction` передают параметры без диалога | Невизуальный запуск, возвращающий `IgsQueryList` без показа формы и печати |
| Описание параметров отчёта | `gd_function.enteredparams` — двоичный список `TgsParamList` (маркеры `SLPR` … `FLPR`): имя, отображаемое название, тип (число, период, ссылка на справочник…) | Парсер в MCP-сервере: читает параметры прямо из реплики для `list_reports` |
| Сериализация | `Dataset2JSON` — только для `IgsIBSQL` | Общий `Dataset2JSON` для любого набора данных и `IgsQueryList` |

**Ограничения, которые нужно учесть:**

- **Воркеру нужна база с возможностью записи.** `gedemin.exe` пишет в базу при входе (журнал событий), а журнал-ордер во время построения пишет во вспомогательные таблицы `AC_LEDGER_ACCOUNTS` и `AC_LEDGER_ENTRIES`. Реплика всё равно восстанавливается раз в сутки, поэтому её можно оставить доступной для записи. Сам MCP-сервер работает с ней отдельным пользователем и только на чтение.
- **Один поток.** Все HTTP-запросы выполняются по очереди в главном потоке воркера. Для нескольких одновременных пользователей нужен пул из 2–4 воркеров и очередь в MCP-сервере.
- **Диалоги блокируют воркер.** `TgdvAcctBase`, клиент отчётов и пользовательские скрипты могут показать `MessageBox` или форму. Нужен режим «без интерфейса», в котором такие вызовы превращаются в исключения, и таймаут на стороне MCP-сервера с перезапуском зависшего воркера.
- **Не все пользовательские отчёты пригодны.** Отчёты, чья функция параметров или основная функция открывает формы, в каталог не попадают. Список пригодных формируется пробным запуском каждого отчёта с тестовыми параметрами.
- **Не пригодно:** старый сервер отчётов в `Gedemin/Report` (DCOM и сокеты) не собирается, в текущую сборку не входит. COM-автоматизация `gedemin.exe` (`IGedeminApplication`) даёт те же возможности, но хрупчее в развёртывании; это запасной вариант.

Для прототипа правки Delphi не нужны: хватает стартового макроса и VBScript-обработчиков. Для пилота добавляются пункты из колонки «Что добавить» и режим без интерфейса.

**Требования ко всем тулам уровня:**

- Каждая сумма сопровождается валютой, а количество — единицей измерения.
- Итоги и сальдо возвращаются всегда, даже если строки обрезаны пагинацией.
- В ответе перечислены применённые фильтры (организация, период, учтены ли внутренние проводки), чтобы модель могла объяснить, что именно посчитано.
- Ошибки понятны модели: «счёт 60.5 не найден, ближайшие: 60.1, 60.2», а не стек исключения.

## Уровень 2: поиск сущностей

Пользователь говорит «Ромашка» или «расчёты с поставщиками», а тулам нужны точные коды и ID. Тулы этого уровня переводят одно в другое.

| Тул | Что ищет |
| --- | --- |
| `find_account` | Счёт по коду, названию или по смыслу («дебиторка покупателей») |
| `find_counterparty` | Контрагент по названию, УНП/ИНН, части названия |
| `find_item` | ТМЦ, услуга |
| `find_document_type` | Тип документа по названию или описанию |
| `find_analytics_value` | Значение произвольной аналитики (договор, подразделение, статья затрат) |

**Требования:**

- Нечёткий поиск: опечатки, раскладка, организационно-правовая форма в начале или в конце.
- Результат — список кандидатов с признаками для различения (код, УНП, адрес, признак архивности). При неоднозначности модель уточняет у пользователя, а не выбирает сама.
- Поиск учитывает текущую организацию.

## Уровень 3: данные документов и SQL

Одних представлений недостаточно. У каждого из сотен типов документов есть своя таблица с реквизитами, которых нет в аналитике проводок. Поэтому модель получает **прямой доступ к таблицам на чтение**. Вместо ручных представлений сервер автоматически строит описание схемы из метаданных системы и сам применяет обязательные фильтры.

### Ядро: небольшой набор представлений

Руками пишутся только 5–10 представлений там, где логика сложная и ошибка стоит дороже всего:

| Представление | Содержимое |
| --- | --- |
| `v_accounts` | План счетов: код, название, родитель, тип, виды аналитики |
| `v_entries` | Проводки с развёрнутыми кодами счетов и названиями аналитик. Две формы: по сторонам и парами корреспонденции (см. ниже про issimple) |
| `v_documents` | Общая часть всех документов: тип, номер, дата, организация, признак наличия проводок. Через него соединяются таблицы типов документов |
| `v_counterparties`, `v_items` | Основные справочники |

**Схема учётного ядра Гедемина.** Проверено по [исходному коду платформы](https://github.com/GoldenSoftwareLtd/gedemin) (`Gedemin/SQL/ac_accounting.sql`, `Gedemin/Transaction`, `Gedemin/Component/gdClosingPeriod.pas`) и скрипту [схематического отображения корреспонденции](https://gsbelarus.com/gs/wiki/index.php/Схематическое_отображение_корреспонденции_счетов_с_помощью_GraphViz).

| Таблица | Что хранит | Ключевые поля |
| --- | --- | --- |
| `ac_account` | Планы счетов, группы, счета и субсчета в одном дереве | `alias` (код), `name`, `description`; `accounttype`: C — план счетов, F — группа, A — счёт, S — субсчёт; `activity`: A / P / B; `offbalance`, `multycurr`; `analyticalfield` (аналитика развёрнутого сальдо активно-пассивного счёта); `lb` / `rb`; флаги аналитик `USR$…` |
| `ac_companyaccount` | Какой план счетов активен у компании | `companykey`, `accountkey`, `isactive` |
| `ac_transaction` | Типовые хозяйственные операции (дерево) | `name`, `description`, `lb` / `rb` |
| `ac_trrecord` | Типовые проводки операции | `transactionkey`, `functionkey` → `gd_function` (код формирования), `functiontemplate`, `documenttypekey`, `documentpart`, `dbegin` / `dend` |
| `ac_record` | Проводка целиком | `transactionkey`, `trrecordkey`, `recorddate`, `documentkey`, `masterdockey`, `companykey` |
| `ac_entry` | Одна сторона проводки | `recordkey`, `entrydate`, `accountkey`, `accountpart` (D/C), `debitncu` / `creditncu` (нац. валюта), `debitcurr` / `creditcurr` (валюта), `debiteq` / `crediteq` (эквивалент), `currkey`, `issimple`, аналитики `USR$…`; копии `transactionkey`, `documentkey`, `masterdockey` из `ac_record` |
| `ac_quantity` | Количество по стороне проводки | `entrykey`, `valuekey` (единица измерения), `quantity` |
| `ac_entry_balance` | Рассчитанное сальдо на дату (кэш) | суммы и аналитики; дата хранится в генераторе `gd_g_entry_balance_date` |
| `gd_document`, `gd_documenttype` | Документы и их типы | `documenttypekey` |

Особенности, которые должны учитывать ядро-представления и примеры SQL:

- **Корреспонденция и поле `issimple`.** Проводка бывает только 1:1, 1:N или N:1: «много ко многим» запрещено триггером. `issimple = 0` стоит у строк той стороны, где их несколько. Сумма пары корреспонденции берётся со стороны «многих», как в штатной процедуре `AC_GETSIMPLEENTRY`: `IIF(corr_e.issimple = 0, corr_e.creditncu, e.debitncu)`. Простое `SUM` после самосоединения по `recordkey` (как в скрипте GraphViz) завышает сумму одиночной стороны: Дт 100 / Кт 60 + Кт 40 даёт 200 по дебету.
- **Аналитики — колонки `USR$…`.** Значение аналитики хранится в колонке `ac_entry`, а колонка с тем же именем в `ac_account` — флаг, что аналитика ведётся на счёте. Аналитикой считаются только поля `USR$`, есть в обеих таблицах (так делает `AcctUtils.pas`). Названия и справочники аналитик берутся из метаданных.
- **Активный план счетов** определяется по `ac_companyaccount.isactive` для компании, а не по имени плана.
- **Субсчета — вложенные множества.** «Включать субсчета» = `child.lb >= parent.lb AND child.rb <= parent.rb`. Правило пишется в описание ядра и в примеры.
- **Внутренние проводки и закрытие периода.** Штатное закрытие периода (`gdClosingPeriod.pas`) переносит сальдо в `ac_entry` проводками Дт X / Кт X по одному счёту датой накануне закрытия, операцией «Произвольные проводки». Поэтому в отчётах есть флаг «включать внутренние проводки». Правило для тулов: внутренние проводки не входят в обороты и аналитику, но учитываются в сальдо. Операции «Проводки за прошлые года» в исходниках платформы нет: это настройка конкретной базы, её смысл проверяется на данных.
- **Сальдо.** Штатные процедуры `AC_ACCOUNTEXSALDO_BAL` и `AC_CIRCULATIONLIST_BAL` считают сальдо от остатка в `ac_entry_balance` плюс проводки после его даты. Ядро и тулы используют их, а не суммируют всю историю проводок.
- **Ссылки на документ.** `documentkey` — документ, по которому создана проводка (в том числе позиция), `masterdockey` — шапка документа. Удаление документа каскадно удаляет его проводки, поэтому в `ac_entry` нет проводок удалённых документов.
- **Классы отчётов** в `Gedemin/Transaction`: `gdvAcctCirculationList` (оборотная ведомость), `gdvAcctLedger` (журнал-ордер), `gdvAcctAccCard` (карта счета), `gdvAcctAccReview` (анализ счета), `gdvAcctGeneralLedger` (главная книга — ещё один кандидат в учётные тулы).
- **Кодировка.** Строки в БД и исходники в WIN1251. Сервер подключается к Firebird с нужной кодировкой соединения и отдаёт модели только UTF-8.

Запрос из скрипта GraphViz (корреспонденция счетов в разрезе типовых операций), исправленный через `issimple`, становится одним из первых примеров в `get_sql_examples` и основой для `get_posting_stats`.

### Таблицы типов документов: автоматическое описание вместо представлений

Генератор читает метаданные системы и для каждого типа документа строит описание:

- таблицы шапки и позиций и как они соединяются с общей таблицей документов;
- поля с названиями на естественном языке и типами;
- ссылки на справочники: поле → таблица → поле с наименованием;
- статистику заполненности: какие поля реально используются, типичные значения для перечислений (без персональных данных);
- готовый шаблон SELECT, соединяющий таблицы документа с `v_documents`.

Описания пересобираются при изменении метаданных. Вручную дополняются только пояснения к неочевидным полям самых важных типов.

### Тулы

| Тул | Назначение |
| --- | --- |
| `search_schema(текст)` | Поиск по названиям типов документов, таблиц и полей: «где хранится ставка НДС», «в каких документах есть склад» |
| `get_document_type_schema(тип)` | Описание таблиц типа документа, связей, полей и шаблон запроса |
| `query_documents(тип, поля, фильтры, группировка)` | Универсальный запрос к любому типу документа. Сервер сам строит SQL по метаданным, разворачивает ссылки в наименования и применяет обязательные фильтры. Покрывает большинство вопросов к реквизитам без написания SQL |
| `describe_views()`, `get_sql_examples(тема)` | Описание ядра и проверенные пары «вопрос → SQL» из отчётов и удачных запросов |
| `run_sql(query)` | Произвольный SELECT по ядру и таблицам документов — для сложных запросов, которые не покрывает `query_documents` (несколько типов сразу, соединение с проводками) |

**Особенности Firebird.** Все запросы идут к реплике в транзакциях только на чтение (read only, read committed). Лимит строк сервер накладывает сам, оборачивая запрос в `SELECT FIRST n ... FROM (...)`. Диалект Firebird 5.0 (CTE, оконные функции, FIRST/SKIP и OFFSET/FETCH; LIMIT не поддерживается) указывается в `describe_views` и в инструкциях: модели часто пишут `LIMIT` и функции других СУБД, поэтому примеры в `get_sql_examples` должны быть на диалекте Firebird. Сообщение об ошибке SQL возвращается модели полностью, чтобы она могла исправить запрос. Реплика обновляется раз в сутки, поэтому каждый ответ тула содержит дату среза данных.

### Защита при прямом доступе к таблицам

- **Только чтение на уровне БД.** Отдельный пользователь БД, транзакции только на чтение, таймаут, лимит строк.
- **Белый список таблиц.** Доступны ядро, таблицы документов и справочников. Служебные и чувствительные таблицы (пользователи, пароли, зарплата) закрыты правами пользователя БД, а не только проверкой текста запроса.
- **Разграничение прав — после пилота.** На пилоте участники видят все данные, `query_documents` и `run_sql` не фильтруют по организациям и правам.
- **Документы без проводок.** Состояния «не проведён» в Гедемине нет: проводки есть у документа, если их сформировал код типовой операции. Иногда оно реализовано искусственно: при определённом значении поля код проводок не формирует. Такое условие выявляется при саммаризации и записывается в карточку операции, а `query_documents` возвращает признак наличия проводок и это поле. Документы без проводок не влияют на сальдо и обороты, но видны в запросах к документам. Аналитические тулы по реквизитам документов (например, продажи по количеству) по умолчанию берут только документы с проводками, чтобы цифры сходились с учётом.

## Аналитические сценарии

Для задач вроде «почему упала прибыль» модель сама строит план анализа и вызывает тулы много раз. Сервер даёт ей для этого четыре вещи: единые определения показателей, аналитические тулы с готовыми сравнениями, доступ к внешним данным и методику анализа.

### Слой показателей

Справочник показателей с привязкой к счетам и аналитике: выручка, себестоимость, валовая прибыль, коммерческие и управленческие расходы, прочие доходы и расходы, чистая прибыль, маржинальность, оборачиваемость задолженности и т. д. Определения хранятся в подробном описании счетов в плане счетов: для счёта или субсчёта указывается, в какой показатель он входит и как (дебетовый или кредитовый оборот, с НДС или без). Сервер читает эти описания и строит из них справочник показателей. Чтобы аналитические тулы считали одинаково, привязка к показателю записывается в едином формате, например «Показатель: Выручка; оборот: Кт; без НДС». Остальной текст описания остаётся свободным пояснением для модели. Сервер проверяет полноту: счета с оборотами, не привязанные ни к одному показателю, попадают в отчёт о расхождениях. Модель не решает сама, какие счета входят в выручку.

Тулы: `list_metrics()`, `get_metric_definition(показатель)`.

### Аналитические тулы

| Тул | Назначение |
| --- | --- |
| `get_pnl(периоды, разрез)` | Отчёт о прибылях и убытках по месяцам или кварталам, с разрезом по подразделениям или направлениям |
| `compare_periods(показатель, период А, период Б, разрез)` | Отклонение показателя с разложением по клиентам, товарам или статьям затрат. Строки отсортированы по вкладу в отклонение |
| `factor_analysis(период А, период Б, разрез)` | Разложение изменения выручки и валовой прибыли на факторы цены, объёма и структуры |
| `get_metric_series(показатель, период, шаг, разрез)` | Динамика показателя для поиска трендов и сезонности |
| `get_top_contributors(показатель, период, разрез, N)` | Крупнейшие клиенты, товары или статьи с переходом к документам |
| `get_receivables_aging(дата)`, `get_payables_aging(дата)` | Старение дебиторской и кредиторской задолженности |
| `get_one_off_items(период, порог)` | Разовые и нетипичные операции: крупные списания, резервы, курсовые разницы, штрафы |
| `export_dataset(запрос)` | Выгрузка набора данных в CSV для расчётов в среде клиента: Codex или выполнение кода в Claude. С лимитом объёма |

Все аналитические тулы считают через слой показателей и возвращают готовые отклонения и доли, а не сырые строки.

### Внешняя среда

- **Основной источник — встроенный веб-поиск клиента** (Claude Desktop, Codex): новости отрасли, изменения законодательства, действия конкурентов.
- **Опционально — тулы с официальными рядами данных**: курсы валют, учётная ставка, инфляция, индексы цен. Источники не ограничены: API национального банка и статистики, отраслевые и биржевые данные, любые открытые источники в интернете. Ряды возвращаются с тем же шагом, что и учётные данные, чтобы их можно было сопоставить. Можно вынести в отдельный MCP-сервер.
- В запросы к внешнему поиску не попадают конфиденциальные данные компании: названия контрагентов, суммы, внутренние показатели.

### Методика анализа

Сценарии анализа хранятся не в коде сервера, а как текст для модели:

- **MCP prompts** — в Claude Desktop выбираются как готовые команды («Анализ отклонения прибыли», «Анализ дебиторки»).
- **Для Codex** — тот же текст в AGENTS.md или в виде скилла. Источник текста один, оба формата генерируются из него.

Пример шагов для «почему упала прибыль»:

1. Уточнить период, базу сравнения (предыдущий квартал или тот же квартал прошлого года) и организацию.
2. Получить P&L за оба периода и динамику по месяцам.
3. Найти статьи с наибольшим вкладом в падение.
4. Детализировать: клиенты, товары, статьи затрат; факторный анализ цена / объём / структура.
5. Отделить разовые события от устойчивых трендов.
6. Сопоставить с внешней средой: курсы, спрос в отрасли, цены поставщиков, ставки, регулирование.
7. Сформулировать выводы и рекомендации.

### Формат аналитического ответа

- **Вывод** — 2–3 предложения с ключевыми цифрами.
- **Факты из учёта** — с указанием тула или отчёта, периода и показателя.
- **Внешние факторы** — со ссылками на источники.
- **Гипотезы** — отдельно, с тем, чем их можно проверить.
- **Рекомендации** — с ожидаемым эффектом там, где его можно оценить по данным.

## База знаний

Модели нужно понимать, как документы превращаются в проводки и что считает каждый отчёт. Эти знания готовятся заранее из исходного кода и данных и отдаются по требованию.

### Карточки типов документов

Для каждого типа документа формируется карточка: назначение, формируемые проводки (Дт/Кт, что за сумма), аналитика, условия ветвления, поведение при отмене проведения.

> **Пример. Счёт-фактура поставщика.** Дт 10 / Кт 60.1 — сумма без НДС; Дт 18 / Кт 60.1 — НДС. Аналитика: контрагент, договор, ТМЦ. Если в шапке стоит признак «импорт», то вместо 60.1 используется 60.2.

Как готовится:

1. VBScript-код формирования проводок прогоняется через LLM, которая составляет черновик карточки.
2. Черновик сверяется со статистикой фактических корреспонденций за период. Расхождения помечаются для разбора.
3. Карточку проверяет и утверждает консультант или бухгалтер.
4. Рядом с карточкой хранится хеш исходного скрипта. Если скрипт изменился, карточка помечается устаревшей и перегенерируется.

### Саммаризация кода типовых хозяйственных операций

Карточка составляется для каждой типовой хозяйственной операции (у типа документа их может быть несколько). Одна операция — один вызов LLM, чтобы контекст не смешивался.

**Вход для модели** (собирается скриптом автоматически):

1. VBScript функции формирования проводок вместе со всеми вызываемыми функциями и подключаемыми скриптами. Зависимости собираются статическим разбором кода. Код берётся из gd\_function через ac\_trrecord.functionkey. Если у типовой проводки есть срок действия (dbegin / dend), карточка его указывает, а если заполнен шаблон мастера (functiontemplate), он подаётся на вход вместе с кодом.
2. Метаданные типа документа: поля шапки и позиций с человеческими названиями. Тогда обращение к полю в коде превращается в «Сумма без НДС», а не в имя колонки.
3. Словарь плана счетов и аналитик: если в коде счета заданы идентификаторами или псевдонимами, модель видит «60.1 Расчёты с поставщиками».
4. Статистика фактических проводок по этой операции за последний год: корреспонденции, число проводок, суммы.
5. 2–3 реальных документа с их реквизитами и сформированными проводками, включая нетипичные случаи.

**Выход** — структурированная карточка (JSON для сервера + текст для модели):

- назначение операции и условия, при которых она применяется, в том числе условия, при которых проводки не формируются вовсе (искусственное «не проведён»);
- список проводок: Дт, Кт, как считается сумма (словами со ссылками на поля), аналитика по каждой стороне, валюта и количество, условие формирования;
- поведение при отмене и повторном проведении;
- побочные эффекты: меняет ли код другие данные кроме проводок;
- **неясности** — места, которые модель не смогла трактовать однозначно. Это обязательное поле: модель не должна додумывать.

**Проверка:**

1. **Сверка со статистикой (автоматически).** Корреспонденция есть в карточке, но не встречается в данных — возможна мёртвая ветка кода. Встречается в данных, но нет в карточке — ошибка саммаризации или ручные проводки.
2. **Проверка предсказанием (автоматически).** Отдельный вызов LLM получает только карточку и реквизиты 10–20 случайных документов и предсказывает их проводки. Предсказание сравнивается с фактом. Расхождение = карточка неполна или неверна, она уходит на доработку с примерами ошибок.
3. **Проверка человеком.** Обязательно для карточек с неясностями или не прошедших пункты 1–2. Остальные — выборочно.

**Порядок и актуальность:**

- Операции обрабатываются в порядке убывания числа документов за год: небольшая часть операций обычно покрывает основную массу проводок. Неиспользуемые операции откладываются.
- Рядом с карточкой хранятся хеш кода со всеми зависимостями, хеш метаданных типа документа и версия промпта. Изменилось что-то из этого — карточка помечается устаревшей и перегенерируется ночным заданием после обновления реплики.
- Карточки хранятся вне БД системы (файлы в репозитории или таблица сервера), чтобы история изменений и правки человека не терялись при перегенерации. Ручные правки подаются на вход при следующей генерации.

### Каталог отчётов

По коду каждого отчёта формируется описание: что считает, какие параметры, какие документы и операции учитывает. Процесс тот же: черновик от LLM, проверка человеком, контроль актуальности по хешу. SQL из отчётов также используется для проектирования ядра-представлений и примеров для `get_sql_examples`.

### Тулы базы знаний

| Тул | Доступен |
| --- | --- |
| `get_document_type_info(тип)` — карточки типовых операций типа документа | всем |
| `get_posting_stats(тип, период)` — фактические корреспонденции с количеством и суммами | всем |
| `get_report_info(id)` — описание отчёта | всем |
| `get_posting_script(тип)` — исходный VBScript проводок | только в режиме разработчика |
| `get_report_source(id)` — исходный код отчёта | только в режиме разработчика |

Перед выдачей из исходного кода убираются секреты: строки подключения, пароли, токены.

## Безопасность и ограничения

Сервер ничего не изменяет в данных. На пилоте участники видят все данные: разграничение прав отложено.

- **Аутентификация.** Общий сервер по HTTPS (транспорт MCP Streamable HTTP). Пользователь входит по логину и паролю учётной системы: сервер проверяет их по БД системы и выдаёт токен по OAuth 2.1, как ожидают удалённые коннекторы Claude Desktop. Для Codex допустим также персональный bearer-токен. Пароли сервер не хранит и не логирует. Сервер публикуется в интернет по HTTPS, так как удалённые коннекторы Claude Desktop подключаются к нему из облака Anthropic. Поэтому нужна защита страницы входа от перебора паролей и ограничение частоты запросов.
- **Права системы — после пилота.** Ограничения по организациям, типам документов, счетам и отчётам проектируются по итогам пилота.
- **Только чтение.** Отдельный пользователь БД с правами только на чтение разрешённых таблиц и представлений, транзакции только на чтение.
- **Нагрузка на БД.** Таймауты на запрос, ограничение числа одновременных запросов на пользователя. Все запросы идут к реплике Firebird, а не к рабочей базе.
- **Размер ответа.** Лимит строк и символов, пагинация, явный признак «результат обрезан».
- **Режим разработчика.** Тулы с исходным кодом доступны только отдельной роли и не видны остальным пользователям даже в списке тулов.
- **Аудит.** Журнал всех вызовов: пользователь, тул, параметры, текст SQL, время, число строк.
- **Персональные данные.** Определить, какие поля (зарплата, паспортные данные сотрудников) закрываются правами пользователя БД или маскируются.

## Инструкции сервера для модели

MCP-сервер передаёт клиенту короткие инструкции (поле `instructions`). В них закрепляются порядок работы и правила ответа. Черновик:

```text
Ты помогаешь пользователю работать с данными бухгалтерского учёта. Доступ только на чтение.

Порядок работы:
1. Найди сущности из вопроса через find_*. Несколько кандидатов — уточни у пользователя.
2. Если вопрос покрывается учётным или аналитическим тулом или штатным отчётом (list_reports) — используй их.
3. Реквизиты документов: search_schema → get_document_type_schema → query_documents. Только если этого не хватает — run_sql по шаблону из описания схемы и get_sql_examples; таблицы документов всегда соединяй с v_documents; SQL — в диалекте Firebird 5.0 (FIRST/SKIP или OFFSET/FETCH вместо LIMIT).
4. Показатели (выручка, прибыль и т. д.) бери только по определениям из list_metrics, не придумывай свои.
5. Для аналитических задач следуй методике из соответствующего сценария: сначала план, потом данные, потом выводы.
6. Чтобы объяснить, откуда взялась цифра, используй get_document_type_info и get_posting_stats.

Правила ответа:
- Не суммируй сам: бери итоги из ответа тула или считай в SQL.
- Всегда называй период, организацию, валюту, источник (какой отчёт или запрос) и дату среза данных: данные — на конец предыдущего дня.
- Ответ, полученный через SQL, помечай: «расчёт не по штатному отчёту».
- Разделяй факты из учёта, внешние факторы (со ссылками) и гипотезы.
- Не передавай в веб-поиск названия контрагентов, суммы и другие внутренние данные.
- Не уверен в трактовке вопроса — уточни, а не угадывай.
```

Текст инструкций и описания тулов дорабатываются по результатам тестового набора. Описание каждого тула должно говорить, когда его использовать, а не только что он делает.

## Тестирование и контроль качества

Качество измеряется на наборе реальных вопросов с эталонными ответами и проверяется при каждом изменении тулов, описаний и инструкций.

**Тестовый набор:**

- 50–100 вопросов, собранных у бухгалтеров, в их формулировках.
- Для каждого — эталон: число из штатного отчёта или проверенный список документов, плюс ожидаемый тул.
- Покрытие: сальдо и обороты, расчёты с контрагентами, поиск документов, нестандартные вопросы под SQL, неоднозначные вопросы (ожидается уточнение).

**Метрики:**

| Метрика | Что показывает |
| --- | --- |
| Точность чисел | Доля ответов, совпавших с эталоном до копейки |
| Выбор инструмента | Доля случаев, когда модель взяла учётный тул или отчёт вместо SQL |
| Уместные уточнения | Модель спрашивает при неоднозначности и не спрашивает без нужды |
| Стоимость | Число вызовов тулов и токенов на ответ, время ответа |

Аналитические сценарии не имеют одного верного ответа. Их оценивает эксперт (главный бухгалтер или финансовый директор) по рубрике: верны ли цифры, найдены ли главные факторы, отделены ли гипотезы от фактов, подтверждены ли внешние факторы источниками, применимы ли рекомендации. Каждый сценарий прогоняется в Claude Desktop и в Codex.

**Постоянное улучшение:**

- Логи `run_sql` регулярно разбираются. Часто повторяющиеся шаблоны превращаются в отдельные тулы или попадают в `get_sql_examples`.
- У пользователей есть способ пометить ответ как неверный. Такие случаи попадают в тестовый набор.
