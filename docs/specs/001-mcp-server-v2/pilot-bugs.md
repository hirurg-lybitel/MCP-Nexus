## Закрытые баги (BUG-01 … BUG-05)

### BUG-01 — `McpError -32601` при входе в чат
- **Причина:** web-клиент вызывал `prompts/list`, а `apps/mcp-server` не объявлял capability `prompts`.
- **Что сделано:** в `create-server.ts` объявлен `capabilities.prompts`; в `apps/web/lib/mcp/client.ts` `listPrompts()` мягко возвращает `{ prompts: [] }` на `-32601`.

### BUG-02 — Выдуманный `companyKey: 1` и ошибка `outputSchema` `-32602`
- **Причина:** `companyKey` был обязателен без серверного дефолта; модель угадывала `1` (`CHART_NOT_FOUND`). После добавления `companyName`/`companyScope` в ответы они отсутствовали в `outputSchema` (`-32602`).
- **Что сделано:** добавлен `apps/mcp-server/src/lib/working-company.ts` (`resolveWorkingCompany`: дефолт единственной рабочей организации из `GD_OURCOMPANY` + валидация переданного ID); `companyOutputFields` подключены во все учётные `outputSchema`; обновлены `SERVER_INSTRUCTIONS`.

### BUG-03 — Алиас счёта (`60`, `62`) вместо `accountKey` → тихие нули
- **Причина:** модель пропускала `find_account` и передавала `accountKey: 60` / `62`; `AC_ACCOUNTEXSALDO_BAL` тихо возвращала `0` для несуществующих `AC_ACCOUNT.ID`.
- **Что сделано:** добавлен `apps/mcp-server/src/lib/account-key.ts` (`resolveAccountKey` → `ACCOUNT_NOT_FOUND` с подсказкой вызвать `find_account`); подключён во все отчётные тулы со счётом.

### BUG-04 — Хвост float в денежных итогах (`823.8639999999999 NCU`)
- **Причина:** суммирование строк в `balance.ts`, `trial-balance.ts`, `journal-order.ts` шло через `Number.parseFloat` (IEEE-754).
- **Что сделано:** добавлен `apps/mcp-server/src/lib/money.ts` (`BigInt` с фиксированным масштабом 4 знака: `formatMoney`, `addMoney`, `subMoney`); в `instructions.ts` и `domain-knowledge.ts` зафиксировано, что `NCU` по умолчанию — белорусские рубли.

### BUG-05 — Таймаут `-32001` на вопросе «Какая выручка и прибыль за 2025 год?»
- **Причина:** `apps/web/lib/mcp/client.ts` вызывал `callTool` с дефолтным таймаутом SDK **60 с** против **120–180 с** у воркера; модель запрашивала полную годовую ОСВ вместо узких тулов по `90`/`99`.
- **Что сделано:** введена константа `MCP_TOOL_CALL_TIMEOUT_MS = 180000` в `client.ts`; обновлены `instructions.ts`, `domain-knowledge.ts` и описание `get_trial_balance` (узкий путь через `find_account` → `get_account_analysis`). В D2 таймаут устранён; сам расчёт единого показателя «выручка/прибыль» относится к этапу 5 (`list_metrics`).

## Постановки открытых багов (BUG-06 … BUG-15)

### BUG-06 — Аномальный `dataCutoff: "9026-08-19"` ломает все вопросы без явной даты

- **Где проявилось:** D3, D4, D5, D6 (и поле `dataCutoff` во всех ответах тулов).
- **Симптом:** на вопрос «как изменились остатки за последний месяц / квартал» модель вызывает `get_balance` на `9026-08-19`, `9026-07-19`, `9026-05-19` и отвечает, что остаток не менялся (`1 340 905.63`). В D3/D4 анализирует период до `9026-08-19`. В D6 вообще отказывается отвечать без даты.
- **Корневые причины в коде и данных:**
  1. `apps/mcp-server/src/lib/data-cutoff.ts` выполняет `SELECT EXTRACT(YEAR/MONTH/DAY FROM MAX(entrydate)) FROM ac_entry` без фильтрации выбросов.
  2. В `BG_NEW_FB5.FDB` есть **350 проводок с опечатками даты** в далёком будущем (`entrydate > 2030-01-01`, максимум `9026-08-19`; даже до 2030 года есть будущие записи до `2028-08-31`).
  3. `apps/mcp-server/src/instructions.ts:15` жёстко требует: *«В ответах смотри dataCutoff — дата последней проводки в базе; «текущий год» считай от неё, не от календарной даты»*. Модель обязана следовать этой инструкции и уходит в 9026 год.
- **Что нужно сделать для исправления:**
  1. **`apps/mcp-server/src/lib/data-cutoff.ts`:** считать рабочий срез с отсечкой будущих опечаток — `WHERE entrydate <= CURRENT_DATE` (с fallback на `MAX(entrydate)` только если все проводки старше/моложе в тестовой фикстуре), а при наличии строк `entrydate > CURRENT_DATE` возвращать дополнительную диагностику (или отсекать всё `> CURRENT_DATE + 31`).
  2. **`apps/mcp-server/src/instructions.ts`:** уточнить правило периода без даты: если пользователь спрашивает «сейчас / на текущий момент / где заморожены деньги / кто крупнейшие должники» без даты — не отказывать (как в D6), а брать дату `dataCutoff` и явно указывать её в первой фразе ответа.
  3. **Тесты:** юнит-тест на `getDataCutoff` с моком БД, содержащей выброс `9026-08-19` и нормальные даты `<= CURRENT_DATE`.
- **Статус:** **Исправлено (2026-11-11).** На `BG_NEW_FB5` `dataCutoff` теперь `2026-10-31`. Повторный прогон D5 (`2026-09-30` → `2026-10-31`, `+649 862.56` бел. руб.) и D6 (срез на `2026-10-31` по сч. 10, 20, 41, 60, 62, 62.4, 76 без отказа) подтвердил исправление.

### BUG-07 — Невозможно получить развёртку сальдо и топ должников/кредиторов с именами контрагентов

- **Где проявилось:** D3 («крупнейшие должники»), D4 («кому давно не платим»), A2 («развёртка 62/60 по клиентам»), B3 («топ-10 должников по 62.1»).
- **Симптом:** чат не может назвать ни одного покупателя или поставщика по имени — отвечает, что в инструменте сальдо вернулась одна строка без контрагентов.
- **Корневые причины в коде и платформе:**
  1. `apps/mcp-server/src/tools/balance.ts` вызывает хранимую процедуру `AC_ACCOUNTEXSALDO_BAL(dateEnd, accountKey, fieldName, ...)`. Эта процедура платформы возвращает **только свёрнутую сумму развёрнутых дебетовых и кредитовых остатков** по аналитике (одну строку на счёт), а **не** список `(analyticsId, analyticsName, debit, credit)`.
  2. При этом при `withSubAccounts: true` и `fieldName: "USR$GS_CUSTOMER"` условие в `balance.ts:163` (`if (withSubAccounts && fieldName.toUpperCase() === 'ACCOUNTKEY')`) вообще **отключает обход субсчетов**, когда передан `fieldName` аналитики!
  3. Отдельного учётного тула для ведомости остатков по аналитике с расшифровкой справочника (`GD_CONTACT` и др. через `AT_RELATION_FIELDS.REFTABLE`) в MCP-сервере нет, а использовать `run_sql` для сальдо модель не решается из-за прямого запрета в описаниях тулов.
- **Что нужно сделать для исправления:**
  1. **`apps/mcp-server/src/tools/balance.ts`:**
     - исправить обход `withSubAccounts: true`, чтобы он работал и при заданном `fieldName` аналитики;
     - добавить учётный тул **`get_analytics_balance`** (либо режим детализации в `get_balance`), который:
       a) проверяет через `AT_RELATION_FIELDS` / `AC_ACCANALYTICSEXT`, что поле аналитики (`USR$GS_CUSTOMER` и т.п.) существует у `AC_ENTRY` и определяет таблицу-справочник (`REFTABLE`, например `GD_CONTACT`, поле наименования `NAME`);
       b) считает на Firebird 5 группировку по аналитике на дату `dateEnd` по ветке `LB..RB` счёта (`SUM(DEBITNCU - CREDITNCU)` на каждого контрагента), разделяя положительные остатки в `debitNcu` (нам должны / наши авансы) и отрицательные в `creditNcu` (мы должны / полученные авансы);
       c) возвращает как полные `totals` по всем аналитикам (для сверки с `AC_ACCOUNTEXSALDO_BAL`), так и топ-`limit` строк с `analyticsId`, `analyticsName`, `debitNcu`, `creditNcu`, плюс дату последней проводки `lastEntryDate` (даёт базовую опору и для D4 до внедрения полного aging на этапе 5).
  2. **`apps/mcp-server/src/instructions.ts`:** указать, что для топ-должников, кредиторов и развёртки счёта 60/62/76 по клиентам нужно вызывать `get_analytics_balance` (а не `get_account_analysis`).
- **Статус:** **Исправлено (2026-11-11).** Добавлен тул `get_analytics_balance` (`analytics-balance.ts`): группировка `AC_ENTRY` по `USR$` аналитике на дату с именами из справочника (`USR$GS_CUSTOMER` → `GD_CONTACT.NAME`), `side=debit|credit|both`, `lastEntryDate`, totals. На `BG_NEW_FB5` топ ДЗ по 62 на 31.12.2025: МакВторВуд `365.28`, ГудАртАвто `358.72`, БелВТИ `99.88`. Повторный чат: **D3** вызывает `get_analytics_balance` и называет контрагентов; **B3** корректно показывает почти нулевой долг на `62.1`.

### BUG-08 — Неоднозначное сальдо в `get_account_analysis` приводит к перепутыванию переплаты и долга
